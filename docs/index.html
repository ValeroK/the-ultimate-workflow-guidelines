The Ultimate Workflow Guidelines

Your AI coding assistant is fast, confident, and forgets everything. This makes it slow down, show you a plan, write the tests first, and remember what it learned. For Claude Code, Cursor, Codex CLI, Gemini CLI and Claude Desktop.

The problem

You ask for a small change. You get 200 lines. Half of them "improve" code you never mentioned.

You ask a question. It guesses instead of asking you back.

You explain a quirk of your project. Next session it's gone, and you explain it again.

Telling it not to do these things doesn't work. An instruction like "always plan first" sits in a file the model reads once and then drifts away from twenty minutes into a long conversation.

"The models make wrong assumptions on your behalf and just run along with them without checking. They don't manage their confusion, don't seek clarifications, don't surface inconsistencies, don't present tradeoffs, don't push back when they should."
— Andrej Karpathy

The behavioral principles in this plugin are derived from those observations. The plan-first workflow, greenfield bootstrap, and per-repo memory pattern are layered on top — operationalizing the principles so the model actually applies them, every turn.

The idea

Stop asking one assistant to do everything in one long conversation.

Split the work into five short jobs. Each one starts fresh, knows only what it needs, does a single thing, hands you the result, and stops.

That's the whole concept. Three things follow from it:

It can't skip a step

Not because it is being watched, but because each step is a separate command you run. There is nothing to skip ahead to. The next step does not exist until you start it.

It can't wander

A job that only reads code is given tools that only read code. Four of the five jobs physically cannot write to your files. Only the build step can.

It can't lose the thread

Each job hands back a document, not a memory. The plan is a file on disk, so when the conversation gets too long and the history is trimmed, the plan is still there.

The cost is honest: five commands instead of one, and you are the one who moves between them. That is the trade. You get a checkpoint you actually read, twice, before any code is written.

The five commands

CommandWhat it doesCan it write?
planSeveral readers explore the code in parallel, then one writes the planNo
testsDrafts a test plan, then four critics try to break itNo
buildWrites the tests, proves they fail, implements, loops to greenYes
reviewFour reviewers, then a skeptic who tries to disprove each findingNo
harvestWorks out which lessons from this feature are worth keepingNo

Four of the five hand you proposals instead of applying them. That is on purpose: a proposal you have to accept is a proposal you actually read.

You do not need all five every time. A typo does not need a plan.

Starting a brand new project?

There is a separate mode for that. It interviews you, writes a PRD, designs the system with you, and sets up the living documents the workflow above then reads. Use it once, on an empty repo.

the-ultimate-workflow-guidelines

Day-to-day work in an existing codebase. Any non-trivial change: new feature, bug fix, refactor.

Produces:

  • A PLAN-<feature>.md on disk with the goal, files explored, a review of the existing design, and every intended deviation argued both ways.
  • A test plan you confirm before code is written.
  • A minimal implementation that respects the patterns already there.
  • Proposals for what to record once it lands.

project-bootstrap-guidelines

Greenfield only. From a blank slate to a project that is ready for feature work.

Produces:

  • PRD.md, with a flow diagram and every framework choice recorded alongside the alternatives.
  • CLAUDE.md, ROADMAP.md, progress.md, and an empty memory.md.
  • A clean hand-off to the workflow above once the first feature is scoped.

The behavioral layer

Both skills apply four principles before any procedural step:

🧠
Think Before Coding — surface assumptions; ask when unclear; name tradeoffs. Don't pick silently when ambiguity exists.
✂️
Simplicity First — minimum code that solves the problem. No features beyond what was asked, no abstractions for single-use code.
🔬
Surgical Changes — touch only what the request requires. No "while I was there" refactors, no formatting drift.
🎯
Goal-Driven Execution — define verifiable success criteria; loop until they pass. Tests-first turns "fix the bug" into "write the test that reproduces it, then make it pass."

The workflow is how to work; the principles are how to think.

Key files and why we need them

Each file in the repo plays a specific role. The two layers — always-loaded vs. lazy-loaded — keep the prompt slim while letting knowledge compound across sessions.

CLAUDE.md

A thin always-on index. Auto-loaded by Claude Code on every turn, which is exactly why it is kept short: everything in it is paid for on every single message, whether it is relevant or not. It is deliberately not a copy of the skill body any more. It holds what has no retrieval cue, and points at everything that does. Why we need it: the constraints nothing would prompt you to go and look up.

memory.md + memory/<topic>.md

Slim index + lazy-loaded topical knowledge. memory.md is a list of one-line pointers, each with a "Read when…" cue (concrete keywords + file globs). The actual content lives in memory/<topic>.md and is only pulled into context when the current task touches the topic. Why we need it: compounds explanatory knowledge across sessions ("here's how auth works", "here's why we picked Postgres") without paying the always-loaded tax.

## Gotchas (in CLAUDE.md)

Defensive warnings, always loaded. Short rules ("Beware:…", "Don't…") that protect future sessions from non-obvious footguns. Why split from memory: different purpose. Gotchas alert; memory explains.

PRD.md (greenfield)

What this project does and why. Source of truth for product questions: users, goals, non-goals, success metrics. Also carries every confirmed framework choice with documented alternatives. Why we need it: the workflow skill reads it before planning any later feature, so the *what* and *why* are never re-litigated.

ROADMAP.md (greenfield)

Milestones and ordering. Where the project is heading; what task closes which milestone. Why we need it: persistent project-level scope, distinct from per-feature plans.

progress.md (greenfield)

Time-ordered log. What changed when, what was decided, what bug surfaced. Why we need it: session-to-session continuity for the working state of the project.

PLAN-<feature>.md (transient, per feature)

The plan for one specific change. Created at workflow step 2; survives context compaction; retired after the feature merges. Why we need it: a written artifact survives a compacted chat; chat threads don't.

rules/*.mdc

Cursor's entry point, and its retrieval mechanism. One thin alwaysApply: true rule, which is Cursor's equivalent of CLAUDE.md, plus a set of alwaysApply: false rules Cursor selects on its own by description. Those on-demand rules are how memory/ is reachable at all on Cursor, which does not follow a pointer list the way Claude Code does. Why we need it: Cursor does not auto-load CLAUDE.md.

skills/*/references/*.md

Templates so the model never has to invent shapes. Plan template, PRD template, ROADMAP template, progress template, project CLAUDE.md template, memory template. Why we need it: consistent output across sessions, and the workflow skill points at them by reference instead of inlining the shape every time.

Gotchas vs Memory — the real distinction

Length is a consequence, not the criterion. The two stores serve different purposes and have different shapes:

## Gotchas (CLAUDE.md)memory/<topic>.md
PurposeDefensive warningExplanatory knowledge
Voice"Beware…" / "Don't…""Here's how…" / "Here's why…"
PostureReactive — alerts to a footgunProactive — builds understanding
Always loaded?Yes — short, in CLAUDE.mdNo — Read on demand

Decision test:

  • Phrasable as "Beware:" / "Don't…"? → Gotcha (CLAUDE.md ## Gotchas).
  • Phrasable as "Here's how X works" / "Here's why we picked Y"? → Memory (memory/<topic>.md).

Worked examples:

LessonGoes where
"Tests need a live Postgres — run docker compose up -d db first."Gotcha (defensive, one-line)
"Imports use @/ aliases, not relative paths."Gotcha (defensive footgun)
"Auth flow: short-lived JWT + refresh in HTTPOnly cookie + library X for validation, picked over Z for latency reason W."memory/auth.md (explanatory, multi-paragraph)
"Schema: UUID v7 for PKs because…; migrations forward-only because…"memory/db.md (explanatory, multi-decision)

What you get on which host

Claude Code can run the five commands as real scripts, so the ordering is guaranteed. Nowhere else can.

Claude CodeCursorCodex / Gemini / Desktop
The five jobs, each with fresh contextYesYes, you invoke themAs prose
Ordering guaranteedYesYou hold the sequenceYou hold the sequence
Only the builder can writeYesYes—
Optional enforcement hooksYesNoNot verified

Cursor keeps most of what matters: separate jobs, a clean context each time, and only one of them able to write. What it loses is the guarantee, and its rule file says so plainly rather than implying otherwise.

There is an optional enforcement layer for Claude Code, which blocks an edit before the plan is confirmed and so on. It is off by default. The details, and the honest limits, are in the gates document.

Claude Desktop (claude.ai)

Requires Pro, Max, Team, or Enterprise plan with code execution enabled.

  1. Download the-ultimate-workflow-guidelines-plugin.zip from the latest release (installs both skills) — or one of the per-skill ZIPs (the-ultimate-workflow-guidelines.zip, project-bootstrap-guidelines.zip) for a one-skill install.
  2. In claude.ai, go to Settings → Features → Skills → Upload Skill and select the ZIP.

Install is per-user; each teammate uploads separately.
